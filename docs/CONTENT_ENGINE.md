## 产品与目录

默认入口是“我的简报、发现、关注、资料库”。“关注”集中承载话题追踪与我的收藏；资料库仅保留原始材料。旧版目标、日程和检查记录的代码已从主分支移除（保存在 `archive/research-g1-g4` 分支），旧个人库未被删除。产品运行路径使用 `backend/northing_signal/briefing/`：

| 模块 | 职责 |
|---|---|
| models / settings | 小型领域契约与独立配置 |
| collect / source_adapters / discover / search_sources | 有界公共采集、官网/目录/榜单适配、必要原文节选及九类主动检索 |
| net | 公网读取边界：HTTPS、固定已校验公网 IP、按原域名校验 TLS、重定向与大小限制 |
| understand | 结构化模型判断、原文定位、数字校验和用量记录 |
| engine / tracking / intent | 事件投影、信息增量、个人排序、意图方案与确认后相关性判断 |
| store | 独立 SQLite、不可变材料版本、追加交互和简报快照 |
| publish | 公开日报：中性排序（不读个人数据）的静态网页与 RSS，只发布摘要与出处链接 |
| service / app | 单个工作者与任务队列、取消、HTTP 与静态网页 |
| evaluate / __main__ | 一个命令入口，检查内容与开发参照 |

没有向量数据库、训练框架、封存树或多层测试签名。

## 内容规则

先判断 AI 在原文中是否有实质作用，再判断新增事实、重要性和可用性。模型发布、研究、工程优化、教程和产业变化都可能值得读；不单凭公司名、热度或标题夸张程度决定价值。

普通材料只有标题时等待原文；部分官方 RSS 只给分类词，也需要补充节选。所有摘要明确受当时取得的材料限制。官方原文可支持发布动作，性能和收益保留宣称方与测试条件。引用定位和数字检查是机械守卫，不代表语义真值已独立验证。

首版采用模型抽取的具体事件框架与原文指纹做聚合，并对已覆盖的短公告做保守去重；允许重要测试、更正与约束变化重新出现。跨语言、跨表述的事件召回仍需扩大误例验证；尚未实现语义向量检索，不能宣传已经具备向量召回。

事件归属自 schema 4 起持久化（`events.py`）。材料首次进入事件时分配，之后不随修订或重新整理移动；只有读者的拆分或合并会改变归属。首次启动时，按原有投影规则回填归属，事件 ID 沿用原来的框架哈希，已有的收藏与反馈不受影响。新材料依次尝试：原文完全相同、框架完全相同、模糊匹配、新建事件。模糊匹配只接受标准化后主体、版本号集合与产品词完全一致，且同一方向、相隔不超过 7 天的情况。曾考虑按词重叠比例（Jaccard ≥ 0.6）匹配，但 “Gemini 3 Pro” 与 “Gemini 3 Pro Image” 会被误并，因此改为完全一致。错误合并会把一条独立新闻藏起来，漏合并只是多出一条重复，所以规则偏向少合并。`tests_reader/test_events.py` 中的 26 组名称对照是按公开命名方式构造的合成样例，不是采集到的真实材料，不代表真实召回率。

阅读操作按版本所属的材料归属到当前事件，所以拆分、合并后，收藏、已了解与反馈会跟着报道走；合并前的旧事件 ID 通过别名继续有效。每次拆分或合并都追加记录在 `event_changes`。

兴趣与有用/无关反馈以有界权重影响排序。第一次打开某个内容版本会自动记一条“已了解”（用户 2026-11-11 要求）；读者撤回后，再打开不会重新标记。已了解只针对相应内容版本；在最近一次更新之后标记的只让卡片变灰，下次更新才移出重点，避免阅读过程中简报重排。收藏、偏好和反馈保存在本地。原始正文或私人历史不会因为排序自动被发送给第三方。

2026-11-24（用户要求突出“增量 + 证据边界”）：简报顶部“距你上次来”以上次来访为界（`store.previous_visit`，30 分钟内的来访算同一次），列出之后首次出现或有新报道、且未读未划掉的事件（`reader/logic.ts` `sinceVisit`）。每个事件带一行按规则生成的依据（`engine.standing`）：谁在陈述（官方、论文、媒体/作者、社区、榜单）、谁报告了测试、几个来源、是否含更正；阅读页和公开日报都显示。媒体文中的测试只写“报告了测试”，不称独立；“未见”只指已收取的报道。“为什么值得读”的提示词改为要求直接写对谁有影响、改变了什么，属于措辞调整，未提升 `POLICY_EPOCH`，已有判断保留，新整理的内容才使用新写法。

## 来源与处理边界

`data/briefing_sources.json` 中固定来源现为 45 个入口，覆盖官方/研究、官网更新、模型目录、论文、公开评测数据、媒体、作者和开源 Release，核心来源优先展示。来源是否可用由实际抓取状态决定；不声称覆盖全网或连续覆盖所有更新。逐项检查及重要性排序见 [来源接入说明](SOURCES.md)。

主动检索扩展为九类，发现页勾选来源后点击“搜索所选来源”，与只搜索本机的“搜索内容”分开。此前仅接入 arXiv 与 GitHub 的主动适配器，并不代表固定订阅池只有这两家。

| 检索来源 | 用途与材料边界 |
|---|---|
| 网页搜索（AnySearch） | 发现官方发布、文档、评测和技术文章；搜索摘要只作线索，必须补读原文后才进入内容整理 |
| arXiv | 研究预印本及摘要，不代表同行评审或结论验证 |
| GitHub | 代码实现、仓库说明；星标门槛仅减少噪声，不证明质量 |
| Hugging Face | 模型目录与模型卡；元数据不作为内容证据，仓库最近更新不等于模型刚发布 |
| OpenAlex | 跨期刊/会议研究索引与收录摘要，明确标为“索引摘要”，不冒充论文全文 |
| Hacker News | 开发者发布和讨论线索；社区正文标为“社区发言”，外链仍需补读原文，提交时间不当作原文发布时间 |
| X / Twitter | 默认检索公开帖子的网页索引；本项目配置自己的 Bearer Token 后使用官方近期帖子检索；社区发言不作为独立验证 |
| 抖音 | 默认检索公开索引中的视频和图文链接；尚未取得站内检索权限，不读取视频字幕或音频 |
| 小红书 | 默认检索公开索引中的笔记链接；尚未接入站内笔记 API，不读取登录后的私人内容 |

每次只查询勾选的来源；单个来源失败不阻断其他来源。搜索结果最多补读两份原文；GitHub/Hugging Face 每方向最多两份明确声明 MIT/Apache/BSD 许可的 README 摘录。网页查询保留 `site:` 等检索语法，并对返回网址再次检查指定网站范围。搜索得到的新站点不会自动变成长期订阅源。来源列表展示九类检索入口及各自未检查、正常、空结果或失败状态；可用性以实际请求为准。社交索引结果只保留三平台的实际帖子/视频/笔记网址，首页、搜索页、用户主页和仿冒域名不会当作帖子；不会把登录壳页面或导航页提升为原文。没有正文的条目保持“搜索线索 · 正文待获取”。

网页搜索和 OpenAlex 默认使用匿名接口，受提供方限额约束；如需要，仅在本项目 `.env` 填写自己的可选 `READER_WEB_API_KEY` / `READER_OPENALEX_API_KEY`，不读取其他项目或技能的凭据。接口依据：[AnySearch 检索](https://www.anysearch.com/docs/api-endpoints/v1-search)、[匿名访问](https://www.anysearch.com/docs/auth)、[OpenAlex](https://help.openalex.org/api/)、[Hugging Face](https://huggingface.co/docs/hub/en/api)、[Hacker News / Algolia](https://hn.algolia.com/api)。

## 关注与收藏

在“关注 → 话题追踪”输入一段自然语言描述。AI 识别目标、场景、主次、关注重点、排除条件、内容标准和检查频率，生成中英文实体及不同用途的检索方向。界面展示推断和覆盖边界，可补充一句话重新理解，或编辑方案。明确区分硬性要求与优先偏好，不应把多个兴趣点擅自变成必须同时满足的门槛。

意图理解只产生草稿，不创建订阅、不搜索资料。用户确认具体方案后才创建或替换追踪；也可确认后暂不启动。确认绑定草稿和最终方案，重复确认不会重复启动，过期草稿不能覆盖新方案。后续扩大或修改范围要重新理解、再确认；旧版关键词话题保留数据并暂停自动检查，重新描述需求后升级。理解失败或未配置模型时明确报错，不使用关键词规则冒充 AI 意图识别。

定时器每 30 秒检查到期话题，与手动刷新共享一个工作任务，忙时等待；频率按确认方案选择约 30 分钟、2 小时、每天或每周。服务停止时暂停，重新启动后继续到期检查。最多 12 个关注，可暂停、恢复或取消。描述只交给本项目配置的模型理解；资料网站仅收到确认方案中的检索词。无站外通知或第三方写操作。

追踪执行确认方案选择的来源。整个服务每 30 分钟最多补查一次来源池、每源最多 3 条；每话题最多补读 2 份原文节选。最多 4 个检索方向，每次执行其中 2 个并轮转，每方向只查询九类来源中的指定一种。AI 按意图和近期来源状态规划，用户可修改来源与检索词；既有确认方案仍保持原范围，需要重新理解并确认才会改变。使用实体、分类与新近程度做廉价候选召回，并留出非字面实体方向的候选位置，不能把召回关键词命中当最终相关性。

候选仍经过基础内容整理，之后根据确认的描述、关注重点、排除条件和筛选标准调用模型判断是否满足意图，最多一批 6 条。只有已通过内容门槛且意图判断相关的当前版本进入意图追踪卡片，并展示“为什么与你有关”。判断按确认方案和材料版本缓存，修改方案后不沿用旧判断；取消后不发布迟到结果。尚未判断的原始线索与被排除的结果分开。它仍受候选召回、节选和模型误判限制，不能宣传全网覆盖或语义零误差。

按用户 2026-11-08 指示，意图理解、纠正、内容整理和相关性判断均不设本项目的每日次数或 Token 总量上限。继续共享实际用量记录；来源或供应商请求失败时保留线索、显示未完成状态，不用未取得的正文填充卡片。

“新进展”按匹配事件的材料版本与本话题已浏览版本比较。打开某条内容会把它当前的全部版本记为所有话题中已浏览（用户 2026-11-12 要求），“全部标为已读”一次清除整个话题；后续更正或新版本会重新出现。取消关注仅归档订阅，不删除已有材料与收藏。

卡片正文、阅读价值与空白区域均可打开独立阅读页；标题继续支持键盘操作。收藏和反馈按钮独立响应。收藏集中在「收藏」页；保存当时版本，后续原文变化或新版本暂未整理时仍能阅读旧收藏。

更新记录保存在 `refreshes`（schema 5）。投影以最近一次完成的更新为界：首次收录于其中的事件标“新”，已有事件在其中出现新报道标“有更新”。服务运行期间每天 0 点和 12 点（读者时区）自动更新，可在偏好中关闭；错过的时间点在下次启动后补一次。周报（`report.py`）只汇总投影中已整理、有依据的事件，不调用模型。

默认每批刷新每个来源最多 10 条，整理 24 条，另补不超过 24 份必要节选；这是单次工作批量，不是每日额度。每日次数与 Token 总量默认均为无限制（API 返回 null），每次请求继续在 SQLite 中原子记账，跨本机进程共享；失败、未知用量与取消仍记录。用量按 `READER_TIMEZONE`（默认系统时区）的零点统计，不会在 64 次处停机；缺少供应商计价时只报告 Token 与次数，不伪造金额。

整理失败按条目记录，不再每次更新都重新消耗 Token：第一次失败等待 1 小时，第二次等待 6 小时，第三次后停止自动重试，资料库显示“整理失败”，可手动重新整理。引文或数字与原文不符直接从 6 小时开始。模型回复缺少、重复或多出条目时，只保存属于本批且通过校验的结果，其余记为失败；回复被截断时把这一批对半拆开重试。供应商请求失败不算材料的错，不记失败次数，本轮停止后续请求。

判断按“规则代”（`POLICY_EPOCH`）区分，不再按提示词哈希区分：只改写提示词措辞时，已有判断继续有效；只有影响判断结论的改动才提升规则代。旧代判断继续显示并标注“按旧版规则整理”，在未整理的新材料之后按预算逐步重判。引入规则代之前、由其他提示词版本写下的判断保留在库中，但不显示。

资料本身永远是待评数据，不执行其中的指令。所有网页正文仅作纯文本呈现，不使用来自来源的 HTML 执行脚本。服务监听本机，不宣称生产鉴权或多用户隔离。

## 本轮真实材料开发检查

已从 12 个来源取得 136 条真实材料，补取 24 份原文节选；显式主题发现又补充 6 条，合计 142 条。在调用候选模型前，AI 从已取得材料中冻结了 46 条开发参照（28 read / 8 skip / 10 uncertain，44 家族）；取得的原文节选、标签和失败输出保存在本地 .local/reader-quality/，不进入公开仓库。

参照按家族保留 development/holdout 标记。该小样本由当前 AI 选择和标注，不能称为独立留出研究；10 条 uncertain 不纳入决定性质量分母。尚未处理或未通过守卫的条目必须计入处理覆盖缺口，不能只报告成功回答上的高准确率。

当前比较把关键词过滤作为简单对照，分别报告处理覆盖、完整准确率和错例。结果随后续处理发生变化，使用上面的 evaluate 命令重新读取，不能沿用未经观察的历史数字。来源扩充收益、事件合并收益和个人排序效果分别解释，未做真人阅读时间或有用性测量。

本次 36 条明确参照全部完成处理；关键词筛选命中 26/36，内容筛选命中 35/36，仍漏掉一篇 AI fuzzing 教程。其余全库中仍有 53 条未完成有效判断，不能把参照覆盖率称为全库处理覆盖率。开发中曾因引文排版、数字换算和模型输出格式拒绝多条结果，修复机械守卫后复核缓存并保留原失败输出；这不是一次盲评，也不是完整事件排序效果比较。
