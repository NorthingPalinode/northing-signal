## 1. 定位与本轮目标

目标用户是经常阅读 AI 官方发布、论文、GitHub、X 和技术文章的人。优先解决重复刷屏、出处难追、宣称与测试混淆，以及离开几天后不知道判断发生了什么变化的问题。

产品定位：**面向重度 AI 读者的事件追踪阅读器：聚合同一事件的发布、测试与更正，保留原始出处，帮助读者看清宣称的依据与边界。**

本轮围绕一个可体验故事开发：读者七天未访问，一项模型发布期间出现转载、发布方自测、第三方测试和条件修正。回访后，读者能先看到重要增量，再核对“谁提出了什么、谁测了什么、测试支持到哪里、后来改了什么”。

简报保持精选，线索发现扩大覆盖；重要但未确认的线索明确标注。证据类型是产品信息，卡片直接显示简短状态，原文、条件和关系在详情展开。

## 3. 开发顺序与交付

工程按 P0 → P1 → P2 → P3 → P4 推进。P0 开始的 14 天外部观察与后续开发并行；工程完成和观察完成分别报告。以下工期是工作量估算，不是已启动的日程。

| 工作包 | 估算 | 可审查的交付 |
|---|---:|---|
| P0 外部漏报与现状诊断 | 1–2 个开发日 | 轻量观察记录、截止时点快照、漏报原因和基线报告 |
| P1 主张与测试归属 | 2 个开发日 | 主张级字段、准确的证据状态、可核对的详情 |
| P2 持续事件与回访增量 | 2–3 个开发日 | 稳定事件关系、完整版本历史、七天回访变化说明 |
| P3 覆盖与 X 原始出处追溯 | 2–3 个开发日 | 有界追溯、按漏报补来源、扩源前后增量比较 |
| P4 对象关注与角色偏好 | 1–2 个开发日 | 快捷关注、保留定制追踪、可解释的偏好排序 |

合计约 8–12 个开发日；以真实错例和接口可用性调整。P1–P2 完成后先交付可体验版本，不等待所有工作包齐全。P5 为后续分发选项，不作为本轮完成条件。

### P0：先知道漏在什么地方

交付：

- 在现有 `evaluate.py` / CLI 上增加轻量外部事件比较，不新建一套评测框架。观察输入先使用本地 JSONL，沿用 `.local/reader-quality/`；无需先开发后台管理页面。
- 开始前登记核心对象/方向、重要性标准、来源范围、日常检查时点和运行方式。优先模型发布、Agent/工程、研究与评测三类；具体核心对象清单在启动观察时登记，之后变更分段记录。
- 每天从系统结果之外查看至少两类公开入口，例如原始发布列表，以及 X/技术作者/另一资讯站。先记录外部事件和为何重要，再检查系统结果，避免只从入选内容倒推参考集。该做法增加发现独立性，不等于独立的人类验证。
- 每条记录包含事件标识、重要性理由、外部出处、原始发布时间（可未知）、外部首次看到时间、检查截止时间、系统当时状态、模型/规则及来源配置版本。
- 截止时点保留系统结果，再进行补采、补正文或重处理。后续修复追加记录，不覆盖原漏报；更新前与例行更新后的结果分别保留。
- 原因区分为未发现、来源失败、正文不足、待处理、错误过滤、错误合并、已收录但未进简报；同一事件只计一次，可附多个原因与后续修复。

验收：能用至少一个范围外、一个未发现、一个待处理、一个仅未上首页的受控案例验证统计口径。先交付基线报告和观察入口；14 天真实观察从实际启用日开始，不能用历史回放或合成输入填满天数。

### P1：把宣称和测试归属做实

交付：

- 在 `models.py` / `understand.py` 中扩展主张：提出者、所指模型/版本、测试执行者、与发布方关系（同方/第三方/未知）、关键方法与条件，以及对应材料版本和原文引句。缺失字段允许未知，不要求模型补齐不存在的信息。
- 分开记录材料形态、发言者身份、主张类型和支持关系。官网不自动表示性能已验证；论文作者的自测不因来源角色为 research 就升级为独立测试；X 也不因平台身份自动失去原始出处资格。
- 卡片可显示“发布方宣称 / 发布方报告测试 / 第三方报告测试 / 归属待确认”等简短状态。更正、撤回属于关系或动作，可以与测试状态并存。
- 详情回答“谁说的、谁测的、测什么、什么条件、支持哪个结论”。“独立测试”仅在测试主体及关系有明确依据时使用；不显示本产品未执行的“我们实测”。
- 新规则使用新的判断版本；旧输出保留，不静默升级证据等级。更新 README 定位句，能力说明只描述已交付部分。

验收：用同一真实事件的发布原文和测试材料核对归属，并补充发布方自测、第三方关系未知、媒体转述和条件不足的反例。审查样本中，所有展示的主张都可追到对应输入版本和引句；已发现的主体、数字、条件或证据等级错误修复后再发布相关内容。

### P2：让事件时间线解释判断变化

交付：

- 在现有 SQLite 中保存稳定事件身份及必要关系，不再只依赖可变化的模型 `event_key` 绑定历史交互。区分“同次发生的重复报道”“有关联的后续测试/更新/更正”“同公司不同事件”。
- 同一模型的不同版本不直接合并；一个测试或更正只关联其实际涉及的主张与版本。向量或词法相似度只提供候选，不能单独决定支持、反驳或合并。
- 读取已保留的材料历史版本；原文修订后，旧引句、收藏、简报快照和已展示记录仍可核对。误合并允许解除或重挂关系，保留原决定和依据；身份调整不丢失收藏与反馈。
- 增加基于证据版本的回访增量：新发布、新测试、支持范围缩小、条件改变、更正/撤回。新转载或纯排版改动不自动计作实质进展。
- 回访基于上次访问或明确的事件已浏览版本比较；展示、打开、已浏览、已了解继续分开。访问首页不代表了解全部事件，旧版本已了解不压住后来更正。
- 重要更正在首页阅读预算紧张时仍有明确入口，可显示“另有关键更正”，不因普通个性化排序消失。

验收：完成“发布 → 多渠道转载 → 自测/第三方测试 → 条件修正”的可读故事。选择少量真实事件核对关系，缺失的真实更正可以用明确标记的合成反例验证机制，但真实更正效果保持待验证。覆盖七天回访、同公司不同发布不误合并、错误归组修正及旧收藏可读。

### P3：按真实漏报改善覆盖，优先打通 X 的线索价值

交付：

- 复用 `search_sources.py` / `collect.py` / `discover.py`，从 X 或媒体线索提取原文链接、明确实体与版本，再有界查询官方公告、仓库 Release、模型卡、论文或测试原文。单条线索最多追溯两跳，并保留发现路径；沿用公共网络读取边界、单批超时与取消。
- 发布者自己的 X 发布帖、测试者自己的测试帖可以成为原始材料；作者归属不明时保留未知。没有取得正文时继续作为线索，不能据摘要生成已确认主张。
- 无 X token 时如实使用公开网页索引；有本项目授权 token 才启用原生 API。两种访问方式分别报告可用性与收益，不将模拟接口测试称为实网接通。
- 从 P0 的主要漏报原因决定动作：未发现则补来源或检索，正文不足则补读，积压则改善处理，错滤/误并则修规则；不把所有漏报都归因于来源太少。
- 只有提供独有重要事件或有效补证的来源才提高投入。抖音、小红书保留现有可选入口，本轮不追加原生接入和视频理解工程。
- 记录每个新增来源带来的独有事件、有效补证、重复量、失败、延迟、模型调用和 Token。不给用户已有确认方案自动扩范围；新的定期检索范围通过明确的关注操作或方案确认启用。

验收：对基线漏报做修复复查，保留原截止时点；在同一批线索上比较追溯前后可取得的有效原文和新增事件。至少验证一个真实公开发现路径；外部接口失败时保留失败状态。只报告实际观察到的扩源收益，不把它计成排序或摘要质量提升。

### P4：降低关注成本，再增加轻量个性化

交付：

- 增加模型、公司、GitHub 仓库、研究关键词四类对象入口；优先支持资料已有实体、明确的 `owner/repo` 和用户选定关键词。区分确定对象与需要消歧的名称，不先建设完整实体目录。
- 对象选择后直接展示对象、范围、来源和频率，用户点击“关注”即确认这份具体设置；无需先调用模型生成意图草稿。服务启动前仍校验设置并记录确认版本，不能绕过取消、幂等和范围约束。
- 复用现有追踪任务与来源适配器，增加明确的对象关注模式；现有仅接受 `intent_plan` 的服务入口需要一并调整。简单对象匹配不伪装成 AI 意图理解；复杂相关性判断按实际需要调用模型。
- 保留自然语言高级需求、方案编辑与确认，用于本地运行、排除云 API、指定测试标准等组合条件。既有关注不自动改模式，重复关注去重，暂停/取消后不发布迟到结果。
- 偏好增加可选角色（研究、工程、产品、投资，可多选）与子方向。先采用可解释的有界排序权重，默认不选角色；角色不作为事实门槛，也不硬过滤跨方向的重要发布或更正。
- “为什么与你有关”引用用户真实选择和材料具体内容；角色变更不触发未经确认的额外来源检索。

验收：简单对象能在同一表单内完成关注；相同对象的重复提交不创建重复任务；高级自然语言仍能表达复杂条件。在同一候选池比较偏好变化，只宣称排序行为可解释，不据此宣称已节省阅读时间。

### P5：观察后决定免部署分发

在 P0–P4 可体验、并取得观察结果后，再评估托管公共只读网页及 RSS。先明确谁运行采集服务、模型费用和可公开发布的内容；本机 RSS 自身不能解决读者免部署。

本轮交付分发取舍建议即可，不部署公网服务、不增加账号体系。邮件、Telegram、飞书仅作为以后用户主动订阅的可选出口；不默认通知，不替用户自动操作第三方系统。是否建设托管版依据内容质量、实际试读反馈和运行成本决定。

## 4. 一份报告回答哪些问题

沿用一个评测入口，结果汇总到内容引擎说明；本地观察输入、原文和私人记录不上传，不新增重复封存清单。

| 观察项 | 口径和本轮目标 |
|---|---|
| 外部事件覆盖 | 先登记范围；分别报告截止时点的已发现、可阅读收录、进入简报的事件数 / 外部重要事件数，以及每条漏报原因 |
| 及时性 | 报告外部首次看到到系统首次可阅读的延迟；尚未收录的保留为未命中，不从分母删除。补报与原截止状态分开 |
| 来源与运行缺口 | 记录服务停机、未执行检索、来源失败和正文不足；它们仍是实际体验缺口，可分层解释，不能以排除分母制造通过 |
| 证据可核对 | 审查样本中的展示主张均有原文版本与引句，归属和关键条件准确；未知明确显示 |
| 重复与更正 | 同次发生的无增量报道不重复占主项；候选目标为前 10 项至多 1 项无增量重复，条数不足按实际条数报告；登记的受控更正故事全部通过 |
| 回访 | 能说明相对于阅读基线新增了什么证据或限制；转载不冒充新变化，更正不被旧“已了解”压住 |
| 阅读价值 | 延续前 10 项至少 8 项符合预登记开发取舍标准的候选目标；AI 标签与用户实际反馈分别报告，未经试读不声称节省时间 |
| 成本与失败 | 报告次数、Token、耗时、失败与未完成数量；没有可靠计价时不伪造费用 |

P0 先取得基线，再在候选改进运行前登记覆盖改善目标与比较范围；不事先把缺少外部分母的“90% 召回”写成既定交付保证。14 天结束时给出原始计数、逐项漏报及变化，样本很小时不做普遍准确率结论。调试过的错例与后续新事件分开，重复 AI 审查不称为独立验证。

- 只为新增风险补少量必要回归：证据错误升级、主张关系、历史版本/身份迁移、回访更正和对象关注生命周期。当前产品及共用公网边界测试、Ruff、前端构建按相关改动运行；前端纯函数改动另跑相应检查。

## 6. 完成判断与首次实施范围

每个工作包完成时交付实际可读结果、相关检查和已知错例，并更新 [内容引擎说明](../CONTENT_ENGINE.md)。本机工程完成、14 天观察完成、真实更正效果和用户收益分别列状态；未验证部分保留未验证，不能合并为“全部验收”。

用户随后要求优先补足数据源，来源接入子任务已先行实施，具体能力与限制见来源接入说明。下一项仍为 P0：外部事件记录格式、截止时点比较、原因分类和基线报告；随后进入 P1。接口可用不能代替外部召回验证，开始观察也不要求先开通所有平台权限或创建账号。

本计划不引入训练、向量数据库、复杂 Agent 基础设施或全天候后台运维。跨语言误并/漏并有明确错例时，可在 P2 内比较轻量语义候选召回，并按收益决定采用；不得只为增加技术栈而建设。

## 7. 依据与历史边界
